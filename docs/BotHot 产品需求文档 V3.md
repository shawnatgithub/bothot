## 1. 背景、定位与 PR/FAQ

### 1.1 市场现状（公开信息，截至 2026-10-18）

> 来源：GrokMag《Grok Bot marketplace》，https://grokmag.com/grok-bot/marketplace/ （2026-10-18 核查）。上线前由运营复核最新数据。

- Grok Bot 现由 **SpaceXSI（前身为 xAI）** 运营；官方市场 `x.ai/bot/marketplace` 当时收录 **35 个模板**。
- 官方从 2026-09-04 起给部分模板打上 **"Verified" 徽章**，但**没有公开评定标准**。
- 用户添加模板时，**自定义代码、脚本、MCP 服务、私有 skills 不会被复制**；分享链接只公开 Bot 的配置。**BotHot 的审计因此只能覆盖公开配置**，这一点必须如实告知用户（见 §5.1）。
- 官方添加流程本身就有一屏列出模板用到的 integrations。**仅列出权限清单不构成差异化**，BotHot 要提供的是风险判断、外发检测和注入检测。
- 2026-10-11 起，Bot 可以在应用内直接推荐模板，官方正在收拢模板的发现入口；同时市面上已有多个非官方模板目录。

### 1.2 市场痛点

1. **官方货架有限，民间模板分散**：官方市场收录门槛高、数量少，大量实用型 Bot 散落在 X 和 GitHub 的公开分享链接中，缺乏统一检索和热度对比。
2. **安全顾虑大**：同一账号下的所有 Grok Bot **共用一台云端计算机和已登录的网页会话**。第三方模板没有独立的安全审计，存在提示词注入和数据外泄的隐患；官方的 "Verified" 徽章也没有公开标准。
3. **热度真伪难辨**：现有目录站只做静态卡片陈列，看不到全网的引用来源，也没有真实复用数据。

### 1.3 产品定位

**BotHot 不是"民间版官方市场"，而是 Grok Bot 生态的"第三方排行榜 + 安全审计站（Leaderboard & Auditor）"。**

- **决策闭环**：用户在站内看排名、查风险等级、核对所需权限 → 点击官方链接跳转到 `x.ai`，按官方流程完成安装。
- **首屏铁律**：首页首屏不能是官方市场那种静态分类网格，必须直接展示**带名次、带风险徽章、带全网引用背书**的排行榜列表。

| 维度 | 官方市场 | 非官方目录站 | **BotHot** |
| ---- | -------- | ------------ | ---------- |
| 收录范围 | 官方收录，数量少 | 人工收集，数量不一 | 官方市场 + 全网公开分享链接 |
| 排序依据 | 编辑精选 / 分类 | 静态陈列 | 全网引用 + 站内真实转化 |
| 安全信息 | "Verified" 徽章，标准未公开 | 通常没有 | 四档风险评级 + 命中规则 + 证据摘要 + 公开的审计方法 |
| 引用溯源 | 无 | 无 | 列出每一条 GitHub / X 引用，可逐条点开核对 |
| 语言 | 英文 | 不一 | 中英双语 |

## 2. 目标与成功指标

### 2.1 北极星指标

**每周自然出站点击数**：用户在 BotHot 内看榜、搜索或筛选后，点击"去 x.ai 官方安装"的次数（口径见 §10.3）。它直接反映"BotHot 是否帮用户做了安装决策"。

### 2.2 指标层级

| 层级 | 指标 | 说明 |
| ---- | ---- | ---- |
| 北极星 | 每周自然出站点击数 | 同一 IP + Session 24 小时内只算一次，排除内部和爬虫流量 |
| 过程指标 | 榜单 → 详情页点击率 | 榜单是否吸引人 |
| 过程指标 | 详情页 → 出站转化率 | 详情页是否帮助用户做出决策 |
| 过程指标 | 每周有效外部投稿数 | 社区供给是否自发增长 |
| 过程指标 | 登录率、7 日回访率 | 种子用户沉淀 |
| 护栏指标 | 🔴 高风险 Bot 的出站点击占比 | 高风险 Bot 不应获得大量流量，阈值 2%（D38，口径见 §2.2.1） |
| 护栏指标 | 申诉推翻率 | 超过 20% 说明规则或审核质量有问题（D38，口径见 §2.2.1） |
| 护栏指标 | 申诉按时处理率、投稿按时审核率 | 目标 100%（申诉 7 天，投稿 48 小时） |
| 护栏指标 | 页面性能 | 见 §12 |

#### 2.2.1 护栏指标的口径与触发动作（D38）

| 指标 | 计算口径 | 触发条件 | 触发后的动作 | 负责人 |
| ---- | -------- | -------- | ------------ | ------ |
| 🔴 出站占比 | 🔴 Bot 的自然出站点击数 ÷ 全站自然出站点击数，按天计算；**全站当天自然出站点击 < 50 时不计算** | **连续 7 天**超过 2% | 复查 🔴 的折叠交互、详情页警示条和安装按钮上方的风险提示文案；1 周内提出改进方案 | 产品负责人 |
| 申诉推翻率 | 结果为"调整档位"（`revised`）的申诉数 ÷ 已结案申诉数（`upheld` + `revised`，**不含自动关闭的 `superseded`**，D44），**按最近 4 周滚动计算**；**已结案申诉少于 5 件时不计算** | 超过 20% | **暂停新规则上线**；复盘规则库和被推翻的判定，找出误判原因；修订规则或审核手册后恢复 | 审核员 A（复盘）、产品负责人（批准恢复） |

- 两项指标都在门槛监控看板（§9.7）中展示，触发时通知产品负责人。

### 2.3 放量门槛（Go / No-Go Gate）

**满足以下任意一条即判定 Go（D15）：**

1. **连续 7 天日均自然出站点击 ≥ 100 次。**
2. **连续 2 周，每周 ≥ 10 条有效外部投稿。** 有效外部投稿指团队成员以外的人提交、且通过审核的投稿（重复投稿、被拒投稿不计）。

**判定规则（D16）：**

- 观察期为**第 4–9 周，共 6 周**。门槛按窗口内**任意连续 7 天 / 连续 2 周**计算。
- 观察期内最多调整 **2 次**榜单维度或内容包装，调整后**不重新计时**。
- 判定为 Go 后，**下一周**启动 Phase 2（最早第 5 周，最晚第 10 周）。
- 门槛数据以运营后台的门槛监控看板为准（§9.7），每周一由产品负责人复盘。

### 2.4 维护模式

第 9 周末仍未达标时进入维护模式：

- 停止新功能开发，不追加任何采集预算；
- 运营每周手动更新一次（处理投稿、补录引用、标记失效链接）；
- 每天的快照任务、申诉处理、投稿审核照常进行，网站保持在线；
- 若维护期间门槛达标，可重新提交 Go 判定。

## 3. 分阶段规划与范围

### 3.1 时间线

| 阶段 | 时间 | 目标 | 关键交付 |
| ---- | ---- | ---- | -------- |
| **第 1 周前置任务** | 第 1 周（与开发同时进行） | 解除外部依赖 | X 开发者账号、法务咨询、供给调查、指定审核员（§17.1） |
| **Phase 1：冷启动 MVP** | 第 1–3 周开发，第 3 周末上线 | 跑通"看榜 → 查风险 → 跳转官方安装"闭环 | 见 §3.2 |
| **观察期** | 第 4–9 周 | 验证真实需求 | 门槛监控、最多 2 次调整 |
| **Phase 2：自动化扩容** | Go 判定后的下一周开工，约 4 周 | 扩大收录规模，建立创作者社区与长尾 SEO | 见 §3.4 |
| **Phase 3：生态护城河** | Phase 2 完成后，按流量和商业化进度投入 | 从单 Bot 排行升级为多 Bot 协作与生态入口 | 见 §3.5 |

> 若供给调查发现合格模板少于 50 个，Phase 1 上线延期，观察期相应顺延（D17）。

#### 3.1.1 首批收录规则（D39、D40）

**合格标准（D39）**：硬性条件全部满足，且价值门槛满足其一。

| 类型 | 条件 |
| ---- | ---- |
| 硬性条件 H1 | 链接能公开访问（不登录或用普通账号就能打开） |
| 硬性条件 H2 | 是 Grok Bot 模板（`x.ai/bot/` 开头的链接） |
| 硬性条件 H3 | 页面信息足够写出一句话摘要，也能看出用了哪些连接器 |
| 硬性条件 H4 | 不是测试、空壳、重复或明显的垃圾内容 |
| 硬性条件 H5 | 内容不违法，没有成人、仇恨等违规内容 |
| 价值门槛 V1 / V2 / V3（满足其一） | V1 收录在官方市场；V2 至少有 1 条非作者本人的外部引用（GitHub 或 X）；V3 被至少 1 个非官方目录收录 |

- 可能判为 ⚪ 或 🔴 的 Bot 同样算合格：照常收录，在榜单中降权或折叠。
- 上线后的投稿也按同一标准审核（§9.4）。

**首批上限（D40）**：合格数 N 超过 100 时，按非自引外部引用数从高到低取前 **100–120 个**作为首批审计（审核工时按 100 个估算，见 D24）；官方市场模板优先纳入。其余合格模板转入审核队列，上线后按每周 20–30 个的节奏陆续审计、上榜【待评审】。报告标题按首批实际审计数量写。

## 4. 数据采集与数据源适配器

### 4.1 Phase 1 数据来源

| 来源 | 方式 | 频率 | 说明 |
| ---- | ---- | ---- | ---- |
| 官方市场 | 运营人工收录 | 上线前一次，之后每周 | 只记录元数据和官方链接 |
| GitHub | GitHub Search API（免费），检索包含 `x.ai/bot/` 的仓库、README 和 Awesome List | **每天一次** | 记录引用仓库、仓库 owner、提交时间 |
| X | 第三方抓取服务**一次性**抓取包含 `x.ai/bot/share` 的推文 | 上线前一次 | **必须在法务咨询通过后执行**（D20）。背书栏注明"X 数据截至 YYYY-MM-DD" |
| X（补充） | 运营人工补录可核实的公开推文链接 | 按需，**每周上限 50 条** | 让 Trending 和新上榜在 Phase 1 有新增数据（D33）。约束见 §4.1.1 |
| 用户投稿 | 投稿页提交 `x.ai/bot/...` 链接 | 实时，48 小时内审核 | 见 §9.4 |

> **Phase 1 只统计 GitHub 和 X 两个渠道**，博客和 Reddit 渠道在 Phase 2 接入。

#### 4.1.1 运营补录约束（D33）

补录让团队有了影响排名的能力，因此必须满足以下约束：

- 只能补录**公开、可访问**的推文，补录时系统校验链接可访问。
- 每条补录都标注 `collected_via = manual`，记录操作人和时间，写入审计日志。
- **团队成员本人发布的推文不计分**（按团队成员 X Handle 名单自动判定 `is_team_citation = true`）。
- 每周（周一 00:00 UTC 起算）补录上限 **50 条**，达到上限后后台禁止继续提交。
- 门槛监控看板**单独统计**每周人工补录数量，以及人工补录引用在 Trending / 新上榜分数中的占比，便于区分"运营投入"和"自然热度"。
- 前台引用列表中，人工收录的引用标注"人工收录"小标签。

### 4.2 数据源适配器（强制架构要求）

- 所有外部抓取逻辑封装为统一接口，与业务层解耦：
  - `fetchXCitations(query, sinceTime): CitationRecord[]`
  - `fetchGitHubCitations(query, sinceTime): CitationRecord[]`
- `CitationRecord` 统一字段：`source_type`、`source_url`、`citer_handle`、`cited_at`、`bot_url`（规范化前）、`raw_meta`。
- 每个适配器支持通过配置切换服务商，**预留 2 家备用服务商**，切换不需要改业务代码。
- D8 的一次性抓取**直接按此接口实现**，Phase 2 直接复用。
- 用于数据抓取的账号和凭证，与用于用户登录的 X 开发者应用**完全隔离**，不共用任何凭证（D20）。

### 4.3 下线预案（D20）

触发条件：收到 X / SpaceXSI 的停止通知、第三方抓取服务被封、或法务建议停止。

1. **24 小时内**停止全部 X 自动抓取；
2. 切换到备用服务商，或改为运营人工收录；
3. 已收录的公开推文链接继续展示，背书栏显示"X 数据截至 YYYY-MM-DD"；
4. 若 X 登录同时失效：登录弹窗提示改用 GitHub 登录；作者申诉临时改为"在 X 上发布一条带验证码的推文"来核实身份；
5. 事件记录到运营后台，并通知产品负责人。

### 4.4 链接规范化与去重

- 统一为 `https://`，去掉 query 和 fragment，统一大小写和末尾斜杠。
- 同一个 Bot 可能同时有官方市场链接（`x.ai/bot/marketplace/bots/{slug}`）和分享链接（`x.ai/bot/share/...`）。**如果两者能确认是同一 Bot，以官方市场链接作为 `official_url`，分享链接存入别名表。** 能否可靠地对应两种链接，需在供给调查中确认【待核实】。
- 投稿、导入、抓取都经过同一个规范化函数，以 `canonical_key` 去重。

### 4.5 原文处理（合规红线）

- 审计时读取的公开配置原文只存在**私有临时存储**中（D34；存储选型与安全要求见 §12，D41）：
  - **保留期**：保留到该版本审计报告发布后 **30 天**，用于两人复核和申诉举证；
  - **申诉延长**：保留期内有正在处理的申诉时，延长到申诉结案；
  - **访问权限**：只有 `reviewer` 和 `admin` 角色可以查看，每次查看写入审计日志；
  - **到期处理**：每天定时任务自动删除到期原文，只保留配置哈希和证据摘要；
  - 未通过审核或被拒绝收录的 Bot，原文在拒绝后 7 天内删除。
- 只持久化：结构化标签、配置内容哈希（`content_hash`，用于发现作者是否修改过配置）、命中的规则、改写后的证据摘要。
- 任何前端页面和接口都不输出原文。

## 5. 安全审计引擎

### 5.1 审计范围声明（必须展示在详情页和方法论页）

> **BotHot 审计只检查 Bot 公开页面展示的配置**（指令、skills 描述、所需连接器）。**无法检查**自定义代码、脚本、MCP 服务和私有 skills。审计结果是风险提示，**不代表 Bot 的实际运行行为，也不构成安全保证**。安装前请在官方页面核对授权范围。

### 5.2 四档评级（D9、D10）

| 档位 | 中文徽章 | 英文徽章 | 含义 | 榜单处理（D11） |
| ---- | -------- | -------- | ---- | --------------- |
| 🟢 | BotHot 审计 · 低风险 | BotHot Audit · Low Risk | 未命中任何风险规则 | 正常排序（×1.0） |
| 🟡 | BotHot 审计 · 中风险 | BotHot Audit · Medium Risk | 用到高危权限，需注意授权范围 | 正常排序（×1.0） |
| ⚪ | BotHot 审计 · 信息不足 | BotHot Audit · Insufficient Info | 依赖无法审计的部分，无法排除风险 | 排序分 ×0.8 |
| 🔴 | BotHot 审计 · 高风险 | BotHot Audit · High Risk | 命中高风险规则 | 默认折叠，不计名次 |

- 徽章**必须同时显示图标和文字**，不能只用颜色区分（照顾色觉障碍用户）。
- 全站不使用 "Verified""Safe" 等词（D9）。

### 5.3 判定矩阵

**判定优先级：🔴 高风险 > ⚪ 信息不足 > 🟡 中风险 > 🟢 低风险。** 命中多条规则时，取最高档。⚪ 排在 🟡 之前，是因为"无法审计"意味着无法排除隐藏的高风险行为。

| 规则 ID | 档位 | 触发条件 | Phase 1 检测方式 |
| ------- | ---- | -------- | ---------------- |
| R-01 | 🔴 | 指令或配置要求把用户数据发送到非白名单域名，或非标准的外部 Webhook | URL / Webhook 正则 + 域名白名单比对，人工确认 |
| R-02 | 🔴 | 疑似提示词注入或隐藏行为：要求忽略用户或系统指令、向用户隐瞒操作、伪装身份 | 中英文关键词库（如 "ignore previous""do not tell the user""不要告诉用户"），人工确认 |
| R-03 | 🔴 | 收集凭证：要求用户提供密码、API Key、验证码，并写入指令、记忆或外发 | 关键词库，人工确认 |
| R-04 | 🔴 | 明确要求**不经用户确认**就执行删除、支付或转账、批量对外发送 | 关键词库，人工确认 |
| R-05 | 🔴 | 包含混淆内容：长 Base64 串、编码字符串、零宽字符等无法直接阅读的指令片段 | 正则 |
| G-01 | ⚪ | 依赖自定义代码或脚本 | 关键词 + 人工判断 |
| G-02 | ⚪ | 依赖自定义 MCP 服务 | 关键词 + 人工判断 |
| G-03 | ⚪ | 依赖私有 skills | 关键词 + 人工判断 |
| G-04 | ⚪ | 公开页信息不完整或无法读取 | 人工判断 |
| Y-01 | 🟡 | 对外发送类权限：发送邮件、发布消息、在社交平台发帖 | 连接器风险表 |
| Y-02 | 🟡 | 代码与仓库写入：GitHub 写入、创建 PR、部署 | 连接器风险表 |
| Y-03 | 🟡 | 修改云电脑文件或执行命令 | 关键词 + 人工判断 |
| Y-04 | 🟡 | 金融与支付类连接器（如 Plaid、Robinhood、Coinbase） | 连接器风险表 |
| Y-05 | 🟡 | 定时 Routine 在无人值守时执行写操作 | 关键词 + 人工判断 |
| Y-06 | 🟡 | 读取高敏感数据：邮箱、云盘、财务数据 | 连接器风险表 |
| — | 🟢 | 不命中以上任何规则 | — |

- **规则库**（关键词、正则、域名白名单、连接器风险表）以配置文件形式交付，审核员可以维护，修改记录进入审计日志。
- **声明了人工审批不能降档**：例如一个要用 Gmail 发信、但声明了"发送前需用户确认"的 Bot，仍判 🟡，并加上"已声明审批"副标签（D10）。
- 规则库初稿由审核员 A 在第 1 周完成，评审会确认【待评审】。

### 5.4 副标签

| 副标签 | 中文 | 英文 | 触发 |
| ------ | ---- | ---- | ---- |
| `approval_declared` | 已声明审批 | Approval Declared | 指令中声明了高危操作前需用户确认 |
| `has_routine` | 含定时 Routine | Has Routine | 配置包含定时任务 |
| `also_<rule>` | 另命中 Y-01 等 | Also flags Y-01 | 档位较高的 Bot 同时命中的较低档规则，在详情页一并列出 |
| `appealing` | 申诉中 | Under Appeal | 作者已提交申诉，尚未处理 |
| `recheck_pending` | 配置已更新，待复检 | Recheck Pending | 检测到 `content_hash` 变化 |

### 5.5 Phase 1 审计流程（D24、D5）

```
脚本初筛（规则库） → 审核员 A 初审打标 → 审核员 B 复核 → 双语安全文案校对 → 发布
```

- **审核员 B 复核范围**：所有 🔴、🟡、⚪ 的 Bot 全部复核；🟢 随机抽检 20%。
- **两人意见不一致时，按更高风险的档位判定**。
- 每个 Bot 约 15 分钟，100 个约 2.5 人天，安排在第 2–3 周。
- 英文为审计文案原稿，LLM 翻译为中文。**风险等级理由、命中的规则说明、权限说明必须人工校对**；中文未校对的，中文页面整张安全卡片先显示英文原文（D5，降级规则见 §7.0.1，D42）。
- 发布后的对外表述是"**首批审计结果 100% 经过人工复核**"，不使用"100% 准确"。

### 5.6 Phase 2 审计流程

- 先走规则库过滤，再调用低成本模型（如 Gemini Flash、GPT-4o-mini）生成结构化安全报告。
- **LLM 判为 🔴 或 ⚪ 的结果必须由人工确认后才能公开**，确认前沿用上一份已发布的报告（新 Bot 则暂不上榜）；🟢 和 🟡 可以自动发布，标注"自动审计"，事后随机抽检 10%（D31）。抽检发现误判时，修正结果并记录误判类型；某一档连续 2 周抽检误判率超过 10% 时，该档临时改为全部人工确认【待评审】。
- Embedding 向量相似度检测衍生变体，相似度阈值【待评审】，归并后在原模板详情页的"衍生变体区"展示。

### 5.7 版本与复检

- 每份审计报告绑定一个配置版本（`bot_version_id` + `content_hash`）。
- Phase 1：运营每周手动复查一次；Phase 2：7 天巡检时自动比对哈希。
- 哈希变化后：保留原档位，加上"配置已更新，待复检"副标签，进入复检队列，**7 天内**完成复检。

### 5.8 申诉流程（D19）

1. **入口**：🔴、⚪、🟡 的 Bot 详情页显示"我是作者，申诉此评级"。
2. **身份核实**：作者用 X 登录，登录 Handle 与 `author_handle` 一致即可申诉。作者 Handle 未知或不一致时，通过联系邮箱提交证明材料，人工核实；X 登录不可用时，改用"在 X 上发布带验证码的推文"核实（§4.3）。
3. **提交内容**：针对哪条规则申诉、申诉理由、补充材料（如说明作者已修改配置）。
4. **处理中**：徽章旁显示"申诉中"，档位暂不变。处理期间如果配置更新、链接失效或 Bot 被下架，申诉自动关闭为"已失效"（`superseded`），规则见 §11.1.4（D44）。
5. **处理人**：由**未参与原判定的人**处理；只有两名审核员时，由产品负责人终审。
6. **时限**：提交后 **7 个自然日内**处理，超时自动告警。
7. **结果**：维持或调整档位，结果和理由（中英文）公开在详情页；所有判定变更写入审计日志。
8. **冷却期（D32）**：同一 Bot、同一配置版本、同一条规则，驳回后 30 天内不能重复申诉；检测到配置哈希变化（作者修改了配置）时可以立即重新申诉，并自动触发复检。申诉页显示冷却期截止日期。

### 5.9 审计方法论公开页（Phase 1）

单独页面 `/{locale}/methodology`，公开：审计范围声明、四档评级定义、判定优先级、全部规则 ID 和描述（不公开具体关键词，防止被针对性绕过）、人工复核流程、排序公式和权重、申诉流程、公正性原则。规则或参数修改时，在页面上记录变更日期。

## 6. 排序引擎

### 6.1 原则

1. **热度与安全分开表达**：排名只反映热度，安全只通过徽章、筛选和惩罚表达，不做加分（D11）。
2. **防单点刷榜**：对数归一化、同作者去重、渠道封顶（D12、D13）。
3. **可复现**：所有分数基于每天的快照计算，参数有版本记录，并在方法论页公开。

### 6.2 Phase 1 冷启动分（ColdStart Score）

```
对每个渠道 s ∈ {GitHub, X}：
  N_s  = 该渠道中引用此 Bot 的去重作者数（同一作者在同一渠道只算一次；作者本人和团队成员的引用不计）
  Ĉ_s  = min(1, ln(1 + N_s) / P95_s)
         P95_s = 所有活跃 Bot 在该渠道的 ln(1 + N_s) 的第 95 百分位（只统计 N_s > 0 的 Bot）

ColdStart Score = Σ w_s · Ĉ_s × 安全系数
展示分（0–100） = round(100 × ColdStart Score / Σ 当前阶段有数据的渠道权重)
```

| 参数 | 默认值 | 说明 | 依据 |
| ---- | ------ | ---- | ---- |
| `w_github` | 0.45 | 单渠道最多贡献 45% | D13 |
| `w_x` | 0.35 | — | D13 |
| `w_blog_reddit` | 0.20 | Phase 1 无数据 | D13 |
| 渠道封顶 | Ĉ_s ≤ 1.0 | 单个大 V 或高 star 仓库无法把分数推高 | D13 |
| 安全系数 | 🟢🟡 1.0；⚪ 0.8；🔴 不计名次 | — | D11 |
| 展示分分母 | Phase 1 为 0.80 | 因为 Phase 1 没有博客和 Reddit 数据，理论最高分是 0.80 | — |
| 小样本处理 | 某渠道 N_s > 0 的 Bot 少于 20 个时，用该渠道的最大值代替 P95；达到 20 个后自动切回 P95 | 避免 P95 不稳定 | D25 |
| 自引判定 | GitHub：仓库 owner 等于作者的 GitHub Handle；X：推文作者等于 `author_handle` | — | D12 |
| 同分排序 | 最近一次被引用的时间更新的在前；仍相同时，收录更早的在前 | 不按安全等级排序 | — |
| 快照时间 | 每天 00:00 UTC | 双语站统一用 UTC | — |

### 6.3 新上榜（D14）

- 收录条件：`first_cited_at` 在最近 30 天内。`first_cited_at` 取 GitHub 提交时间和 X 推文时间中更早的一个。
- 按 ColdStart Score 排序；🔴 的处理规则同总榜。
- 一个 Bot 可以同时出现在总榜和新上榜。

### 6.4 名次变化与 NEW 标签（D26）

- 上线后前 7 天**不展示**名次变化，首批 Bot 也不标 NEW（它们都是同一天入榜，没有区分度）。
- 第 8 天起，展示**与 7 天前快照相比**的名次变化（↑3 / ↓2 / —）。不用日环比，因为 Phase 1 的 X 数据是静态的，日环比大多数时候是 0。
- 7 天前不在该榜单上的 Bot（比如新收录的），不显示名次变化，改为显示 "NEW"；首批之后新收录的 Bot，首次入榜 7 天内显示 "NEW"。
- 前台标注说明："名次变化为与 7 天前相比"。

### 6.5 Trending（本周飙升，上线第 15 天开放，D7）

```
对每条在最近 7 天内新增的引用 c：
  衰减权重 d(c) = (2 / (age_days(c) + 2)) ^ G        # 当天的引用 d = 1
Trending Score = Σ_s w_s · ln(1 + Σ_{c ∈ s, 近 7 天} d(c)) × 安全系数
周涨跌幅 = (近 7 天新增引用分 − 前 7 天新增引用分) / max(前 7 天新增引用分, 1)
```

- `G` 默认 **1.8**，正式版开放后用实际数据校准（D27）。衰减公式借鉴自 **Hacker News**（V2 误写为 GitHub Trending）；因为引用数据按天快照，时间单位从小时改为天。
- 入榜门槛：近 7 天至少有 **3 个**新增去重引用作者（D27）。
- **开放条件**：上线满 14 天，**且**近 7 天有新增引用的 Bot ≥ 10 个。Phase 1 的 X 数据是静态的，Trending 主要依赖 GitHub 每日刷新、运营补录和投稿，可能达不到开放条件。
- **简化版兜底（D27）**：上线第 15 天如果不满足开放条件，Tab 先上线简化版 **"本周新增引用"** 榜，满足条件后在下一次快照时自动切换为正式 Trending：

  | 项目 | 简化版"本周新增引用" | 正式 Trending |
  | ---- | -------------------- | ------------- |
  | Tab 名称 | 本周新增引用 / New Citations This Week | 本周飙升 / Trending |
  | 排序分 | `Σ_s w_s · ln(1 + n_s)` × 安全系数，n_s 为近 7 天该渠道新增的去重引用作者数，**不做时间衰减** | 上面的衰减公式 |
  | 入榜门槛 | 近 7 天至少 1 个新增去重引用作者 | 至少 3 个 |
  | 每行展示 | "本周新增 N 条引用" | 周涨跌幅（如 `+145%`） |
  | 空榜时 | 显示空状态和投稿入口 | — |

  切换为正式版后不再切回；如果之后某周正式版入榜的 Bot 不足 10 个，照常展示，不回退。

### 6.6 Phase 2 综合分（暂定）

```
Total Score = 0.60 · 外部引用分 + 0.15 · 衍生变体分 + 0.25 · 站内信号分      (× 安全系数)
站内信号分 = f(自然出站点击, 加权 Upvote, 收藏数)，各项同样用对数归一化并封顶
```

- 自然出站点击的权重**明显高于** Upvote（延续 V2 的思路）。
- 过了放量门槛后，用 Phase 1 记录的投票和点击数据**回放计算**，校准权重后再上线（D6）。

### 6.7 投票与账号加权（Phase 1 记录，Phase 2 计分）

| 账号 | 条件 | 权重 |
| ---- | ---- | ---- |
| GitHub | 注册不满 30 天 | 0.2 |
| GitHub | 注册 30–180 天 | 0.6 |
| GitHub | 注册超过 180 天，且有公开活动（公开仓库或贡献） | 1.0 |
| X | 注册不满 30 天 | 0.2 |
| X | 注册 30–365 天 | 0.6 |
| X | 注册超过 365 天 | 1.0 |

- 权重规则**取决于 OAuth 能读到的字段**，确认 X 开发者账号档位后再定【待核实】。
- 一个用户对一个 Bot 只能投一票，可以撤销；同时绑定 X 和 GitHub 的用户，取较高的权重。
- Phase 1 前台展示的是**原始票数**，账号权重只记录不展示。

### 6.8 参数管理

- 所有参数存于 `ranking_params` 表，按版本管理；修改需产品负责人批准，修改记录写入审计日志。
- 每次快照记录使用的参数版本号，保证结果可以复现。

**US-01 浏览总榜（P0）**

## 10. 埋点与指标字典

### 10.1 原则

- **出站点击以自建事件表为准**，用于门槛判定，不依赖第三方统计工具。
- 页面浏览等一般性指标可以用 Plausible / Umami 等隐私友好型工具【待评审】。

### 10.2 事件表

| ---- | -------- | -------- | ---- |
| `page_view` | 每次页面加载 | `page_type`、`locale`、`bot_id`、`referrer`、`utm_*` | 流量 |
| `board_view` | 榜单渲染完成 | `board_type`、`filters`、`page` | 榜单使用 |
| `filter_apply` | 应用筛选 | `filter_key`、`value` | 筛选器使用 |
| `search_submit` | 提交搜索 | `query`、`result_count` | 搜索需求 |
| `bot_card_click` | 点击榜单中的 Bot 进入详情页 | `bot_id`、`board_type`、`rank_position`、`source_page` | 榜单 → 详情页点击率 |
| **`outbound_click`** ★ | 点击"去 x.ai 安装" | `bot_id`、`source_page`、`board_type`、`rank_position`、`entry_type`、`locale`、`referrer`、`session_id`、`is_excluded`、`exclude_reason` | **北极星指标与放量门槛** |
| `upvote` / `upvote_cancel` | 投票 / 撤销 | `bot_id`、`provider` | 投票数据 |

| `locale_switch` | 切换语言 | `from`、`to` | 双语使用情况 |

### 10.3 "自然出站"与"直链出站"的判定（D15、D18）

- 前端在 `sessionStorage` 中记录本次会话进入详情页的方式 `nav_source`：
  - 从榜单、搜索结果、筛选结果点进详情页 → `board` / `search` / `filter`；
  - 从外部链接或直接打开详情页 → `external`。
- 判定规则：
  - 在首页榜单的卡片上直接点"去 x.ai 安装" → **自然出站**；
  - 在详情页点击，且 `nav_source ∈ {board, search, filter}` → **自然出站**；
  - 在详情页点击，且 `nav_source = external` → **直链出站**（不计入门槛）。

### 10.4 实现、去重与排除

- 实现：按钮是普通的 `<a href="https://x.ai/bot/...">`，点击时用 `navigator.sendBeacon` 发送事件，**不做中转跳转**（D18）。广告拦截插件造成的漏记接受不修，相当于门槛判断更保守。
- 去重：Redis 键 `ob:{bot_id}:{hash(ip + session_id)}`，有效期 24 小时；有效期内的重复点击记录为重复，不计数。
- 排除（`is_excluded = true`）：
  - 爬虫和已知机器人 User-Agent；
  - 无头浏览器（如 `navigator.webdriver = true`）；
  - 团队流量：后台角色用户、内部 IP 列表、访问过后台的浏览器（写入内部标记 Cookie）。

### 10.5 隐私

- IP 只以**每日更换盐值的哈希**形式入库；原始 IP 只在 Redis 中保留 24 小时用于去重。
- **原始事件保留 6 个月**（D35），到期后自动删除明细，只保留 `in_site_metrics_daily` 等按天汇总的数据（汇总数据不含 IP 哈希和 `session_id`，长期保留）。
- Phase 2 回放校准（D6）需要的 Phase 1 明细，按时间线（最晚第 10 周启动 Phase 2）仍在 6 个月保留期内；Phase 2 启动时先导出一份**脱敏后的回放数据集**（去掉 IP 哈希和 `session_id`），供权重校准使用。
- EU/UK 访客首次访问时显示 Cookie 同意横幅；拒绝分析 Cookie 时，出站点击仍然记录，但不写 `session_id`，只按 IP 哈希去重【由法务确认】。

### 11.1 核心实体状态机与联动（D43、D44）

**总原则：风险变高立即生效，变好等次日。**
- **立即生效**（失效、评级升到 🔴 或 ⚪、下架）：详情页立即更新，并触发**当日快照重算**，榜单同步生效。
- **次日生效**（新 Bot 上榜、评级降低、失效后恢复）：等次日 00:00 UTC 快照。这样每天的榜单可以复现，也避免当天的排名被刷。
- **"立即"的含义**：状态变更后 **5 分钟内**前台可见（按需重新生成页面）。
- **显示数据来源**：详情页的徽章和状态实时读取当前报告与 `bots.status`；榜单的名次、分数和徽章读取快照（`rankings_snapshot.safety_level`）。因此评级降低时，榜单会在次日之前继续显示较高的风险档位，这个偏差偏向保守，可以接受。

#### 11.1.1 `bots.status`

```
                 首份报告发布
   ┌─────────┐ ───────────────▶ ┌────────┐   链接失效    ┌──────────┐
   │ pending │                  │ active │ ───────────▶ │ archived │
   └─────────┘ ◀─────────────── └────────┘              └──────────┘
     │   ▲        （不回退）                                  │
     │   └────────────── 链接恢复，重新审计 ──────────────────┘
     │ 审计判定不合格
     ▼
  ┌──────────┐        任意状态 ── 管理员下架 ──▶ ┌────────────┐ ── 管理员恢复 ──▶ pending
  │ rejected │                                   │ taken_down │
  └──────────┘                                   └────────────┘
```

| 状态 | 含义 | 详情页 | 榜单 | 搜索 / sitemap |
| ---- | ---- | ------ | ---- | -------------- |
| `pending` | 已收录，审计未发布 | 不公开（404） | 不上榜 | 不收录 |
| `active` | 正常 | 正常 | 按快照 | 收录 |
| `archived` | 原链接失效（D22） | 标注"已失效"，隐藏安装按钮，保留历史最高名次；连续 30 天后 noindex | 立即移出（触发重算） | 搜索仍可找到并标注"已失效"；30 天后移出 sitemap |
| `rejected` | 审计判定不合格（不满足 D39） | 不公开（404） | 不上榜 | 不收录 |
| `taken_down` | 因侵权、违规或权利人要求下架 | 返回 410 | 立即移出（触发重算） | 立即移除 |

- `archived` → `pending`：链接恢复后必须重新审计；审计期间详情页继续显示"已失效"，审计通过后在**次日**快照上榜。
- `taken_down` 只能由 `admin` 操作并填写原因；恢复时回到 `pending`，必须重新审计。

#### 11.1.2 `verification_reports.status`

```
draft ──A 初审提交──▶ in_review ──B 复核完成（或 🟢 未被抽中）+ 校对状态确认──▶ published ──新报告发布──▶ superseded
```

- 每个 Bot 只有一份 `is_current = true` 的报告，即最近一份 `published`。
- 复检期间（配置哈希变化）：旧报告保持 `published` 并显示"待复检"；新报告发布时，旧报告变为 `superseded`。
- Bot 被判为 `rejected` 时，其未发布的报告标记为 `superseded`。

#### 11.1.3 `submissions.status`

| 投稿的链接对应的 Bot 状态 | 投稿结果 | 附加动作 |
| ------------------------- | -------- | -------- |
| 不存在 | 审核通过 → `approved`，新建 Bot（`pending`） | 进入审核工作台 |
| `pending` / `active` | `duplicate`，提示"已收录"并给出链接 | — |
| `archived` | `duplicate` | 自动生成一条"复查链接"任务给运营：链接可能已恢复 |
| `rejected` | `duplicate`，提示"已评估未收录" | 运营可手动重新评估 |
| `taken_down` | 自动 `rejected`，原因"已下架" | — |

#### 11.1.4 `appeals.status`（D44）

```
open ──▶ upheld（维持） / revised（调整档位）
open ──▶ superseded（已失效，系统自动关闭）
```

- **自动关闭为 `superseded` 的情况**：申诉处理期间检测到配置哈希变化（`config_changed`）、Bot 被标记失效（`archived`）或被下架（`taken_down`）。
- **自动关闭后**：
  - `config_changed`：Bot 转入复检；复检报告发布后，作者可**立即**重新申诉（D32 冷却期不适用）。
  - `archived`：链接恢复并重新审计后，作者可重新申诉。
  - `taken_down`：不可重新申诉，按侵权与下架投诉通道处理（§14.1）。
- **`superseded` 不计入申诉推翻率**（D38），也不触发冷却期。
- **通知作者**：Phase 1 不做站内通知，作者在个人页和申诉页看到状态与原因（中英文）；申诉时填写了选填的联系邮箱的，同时发送邮件（需要事务邮件服务，研发第 1 周选型，见 §17.3）。申诉结案（`upheld` / `revised`）也按同样方式通知。

#### 11.1.5 联动总表

| 触发事件 | `bots.status` | 报告 | 申诉 | 榜单 | 详情页 |
| -------- | ------------- | ---- | ---- | ---- | ------ |
| 投稿审核通过 | 新建 `pending` | 新建 `draft` | — | 不上榜 | 404 |
| 首份报告发布 | `pending` → `active` | `published` | — | **次日**快照上榜 | 立即公开 |
| 链接失效 | → `archived` | 不变 | `open` → `superseded` | **立即**重算，移出 | 立即显示"已失效"，隐藏安装按钮 |
| 复检后升到 🔴 或 ⚪ | 不变 | 旧 `superseded`，新 `published` | — | **立即**重算 | 立即更新 |
| 复检后 🟢 ↔ 🟡 | 不变 | 同上 | — | 次日快照（不影响分数） | 立即更新 |
| 申诉成功、档位降低 | 不变 | 同上 | `revised` | **次日**快照 | 立即更新 |
| 配置哈希变化 | 不变 | 旧报告加"待复检"，新建 `draft` | `open` → `superseded` | 不变 | 显示"待复检" |
| 链接恢复 | `archived` → `pending` | 新建 `draft` | — | 审计通过后**次日**上榜 | 审计期间仍显示"已失效" |
| 管理员下架 | → `taken_down` | 不变 | `open` → `superseded` | **立即**重算，移出 | 410 |
| 管理员恢复下架 | `taken_down` → `pending` | 新建 `draft` | — | 审计通过后**次日**上榜 | 404 |

#### 11.1.6 日内快照重算规则（D43）

- **触发**：`archived`、`taken_down`、复检后升到 🔴 或 ⚪。
- **只重排，不重新取数**：沿用当日 00:00 UTC 快照的引用数据和参数版本，只对受影响的 Bot 做处理（移出 / 折叠 / 分数 ×0.8），其余 Bot 按原分数重新编排名次，生成新的 `revision`。日内新增的引用和投票都不会提前进入当天排名。
- **记录**：每次重算写入 `snapshot_revisions`（触发类型、触发 Bot、操作人）。
- **名次变化**：`rank_delta_7d` 与 7 天前那一天的**最终修订版**比较。
- **页面**：重算后触发首页、各榜单页和受影响 Bot 详情页按需重新生成。
- **防抖**：同一 Bot 1 小时内的多次变更合并为一次重算【待评审】。

**索引建议**：`rankings_snapshot (board_type, snapshot_date, rank)`；`citation_signals (bot_id, source_type)`；`outbound_click_events (created_at, entry_type, is_excluded, is_duplicate)`；`bots` 的名称与摘要建 `pg_trgm` 索引用于搜索。

**原文私有存储的要求（D41，与选型无关）**：

- 私有桶，禁止公开访问，启用静态加密。
- 访问凭证只放在服务端；审核员通过后台代理查看原文，每次查看写入审计日志（D34）。
- 存储路径统一为 `raw/{bot_id}/{version_id}`。
- **删除以应用层为准**：D34 的保留期（报告发布后 30 天，有申诉延长到结案）不是固定天数，由每日定时任务按 `bot_versions.raw_expires_at` 删除。

- 上线检查清单增加一项：存储桶确认为私有，用匿名请求访问返回拒绝。
